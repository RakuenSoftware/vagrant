# Project scope

- Project Vagrant is a C# game consumer of `RakuenSoftware/wol-engine`, whose binary release is vendored at `addons/wol_engine`. Runtime code is C# on Godot 4.7.2 .NET; no GDScript. Reusable engine behaviour belongs in wol-engine with one owner; game rules, content adapters and scenes belong here.
- Extracted game rules belong in `gameplay/Vagrant.Gameplay.csproj`, an ordinary .NET library with no Godot or backend references; it may reference the plain .NET `WolEngine.Core` contracts. Host scenes compose it through .NET-typed boundaries; reusable device and presentation operations belong in wol-engine. Keep Vagrant-specific rules here and remove displaced host calls as each boundary is extracted.
- Character/weapon and animation decoding belongs in the portable gameplay library. It produces `Wol.Engine.Models` data; Godot resource construction and glTF export belong to wol-engine's `RiggedModel3D`. See `docs/ENGINE_CONTRACT.md` for the remaining boundaries.
- Retail catalog and installation rules live in the plain gameplay library; its catalog is an embedded .NET resource. Disc I/O and content-pack mechanisms belong to `WolEngine.Core`; Godot executable discovery and media processes belong to the engine backend. Host resource-cache preparation stays in `RetailContent` until its rendering dependencies are extracted.
- Only players with their own US Vagrant Story disc (SLUS-01040) can play. There is one installation: the disc's files, verified against the retail digest and kept byte for byte (`disc/`, with `install.json` recording where each starts on the disc). It is never versioned or converted. The game decodes what it needs from those files at runtime; what is slow to decode may be kept in `cache/`, which can always be made again.
- Every behaviour is implemented exactly once: one decoder per disc format, one handler per script opcode, one owner for each piece of logic. Reuse and move existing code to its owner rather than writing a second copy. Never commit, ship, download or bundle anything from the disc, and never add fallback content that lets the game run without a verified disc.
- This is not a decompilation project. ser-pounce/rood-reverse is reference material for formats and behaviour only: do not copy its code, tooling, data, tables or text. Write independent implementations.
- Roadmap order: the title (done), every title menu item plus a Settings item like Xeno's, the opening scene playing and rendering correctly, then gameplay after it. Verify each step before starting the next.
- Do not add helper, utility or wrapper layers; put behaviour in its owning type.
- Logic checks run headless. Rendering and UI checks run on an isolated display (`gamescope --backend headless …`), never on the user's desktop.
- Disc images, installations, captures and run output stay local and ignored.
